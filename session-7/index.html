Kronecker v2 — the dynamic byte window

Kronecker embeddings build a token's vector from its UTF-8 bytes, and see only the first 32 of them. For English that is 32 characters. For Tamil it is ten — and past that, distinct words silently become the same vector, permanently.

“Today Kronecker is limiting to presenting 32 position for every word (even apple or a as well). That's a waste of space. What can we do? How can it be dynamic and doesn't force us to crop a word… What can we do with indic?”

01The waste is real. The collision is fatal.

I trained a 131,072-token BPE vocabulary — the V5 number — on the Session 3 India-first corpus, and encoded every token. Two different damages fall out, and the assignment names only the milder one.

Truncation — bytes past the window are dropped. Lossy, but the token still exists.

3,241 tokens (2.47%) exceed 32 bytes.

Collision — two distinct tokens agree on their first 32 bytes, so they get byte-identical codes and identical embedding vectors, forever.

1,154 tokens in 460 clusters. Nothing errors.

A Tamil token is 61× more likely to be destroyed than a Latin one. Not because Tamil is harder — because UTF-8 spends three bytes per character on Brahmic scripts and one on ASCII, so the same 32-byte window is a 10-character window.

A model on Kronecker v1 cannot distinguish “was used” from “that uses” in Tamil, or “Australia” from “Australian” in Hindi. Not “finds it hard” — cannot, at any scale, for any compute, because the two inputs are literally the same vector.

02Widening the window is not the fix

The obvious response is to raise pos_dim to 48 or 64 — which is what the session proposes measuring. Measured, it is a bad trade: it buys an asymptote, not a fix, because any fixed window can be exceeded.

03The insight: this is the positional-encoding problem, again

Session 7 §11 diagnoses the absolute learned position table: “there is no signal in the parameters that connects row 4,095 to row 4,096, because they were only ever independent rows in a lookup table.” The byte-position factor in Kronecker v1 is the same object with the same defect — and the field already knows the fix.

Stop storing position. Start computing it.

v1: κ(t) = z( (1/√L) Σ onehot₂₅₆(byte_p) ⊗ onehot₃₂(p) ) L = min(len, 32) ← caps v2: κ(t) = z( (1/√L) Σ onehot₂₅₆(byte_p) ⊗ φ(p) ) L = len ← no cap
  • No cap. φ is defined for every p, so nothing is cropped — the 751-byte token in the real vocabulary encodes fine.
  • Width decouples from the window. K = dim(φ) is a resolution choice, not a length limit. K = 8 still represents a 700-byte token.
  • The waste disappears at its root. v1 reserves one slot per position; a computed basis spends K dimensions regardless of length, so a and apple stop each reserving 32.

The recommended codec is hybrid — half sinusoid, half fixed-random. The sinusoidal half keeps shared spellings close (Kronecker's stated benefit); the random half supplies the near-orthogonality that drives hard pairs apart.

04Proof — a task v1 provably cannot learn

Same shape as the Session 2 experiment that pinned a token-only model at chance. Take 24 real colliding pairs and ask the smallest possible question: given the token, which one was it? Under v1 the two inputs are the same vector, so the input carries zero information about the label and accuracy is pinned at exactly 50%. The script asserts the bit-identity numerically before training — verified, not argued.

05The negative result that matters

The most literal reading of “don't waste 32 slots on a” is to rescale position by token length, so a short token spreads across the whole basis. I built it. It is the wrong answer, and that is worth more than another win.

Rescaling position destroys prefix structure: train and training no longer align, because the same letter sits at a different normalised position in each. Fixing the waste by rescaling costs the very property Kronecker exists to provide. The fix must come from an unbounded absolute basis, not a normalised one.

Honest limits. The LM runs are d_model 256, 4 layers, 662k tokens — this shows the codec is not worse and far cheaper; it does not establish behaviour at 40 B. The margin on hard pairs is small (~0.002 worst-case cosine) — nonzero and sufficient for the probe, but the random half of hybrid is what keeps it from degrading at long lengths. 45 MB is thin for a 131 k vocabulary, so absolute counts would shift on a production corpus; the asymmetry between scripts is structural and would not.
